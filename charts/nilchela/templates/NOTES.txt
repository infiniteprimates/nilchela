nilchela {{ .Chart.AppVersion }} -> release "{{ .Release.Name }}" in namespace "{{ .Release.Namespace }}".

Installed with NO toolchains, deliberately: the chart ships an empty [tools]
map, because which tools an agent needs is your policy, not the chart's. The pod
runs either way — it just has nothing on PATH yet.

Pin what you want:

  # one tool, one key
  helm upgrade {{ .Release.Name }} <chart> --reuse-values --set tools.go=1.27.1

  # or a tool with options (see mise.toml.example for the full reference)
  helm upgrade {{ .Release.Name }} <chart> --reuse-values \
    --set tools.rust.version=1.83.0 --set tools.rust.profile=default

`tools` is rendered into the chart's mise.toml, so there is no ConfigMap key to
escape and no `--set-file` dance.

First start installs the pinned set into /tools, which can take a few minutes on
a cold volume and is near-instant afterwards:

  kubectl -n {{ .Release.Namespace }} get pods -w
  kubectl -n {{ .Release.Namespace }} logs -f <pod> -c install-tools

Bumping a tool is a values change and a roll — the image never rebuilds.

Toolchain env is the second half of that setup, and it is a separate key because
it is a separate decision. `toolEnv` is rendered into the chart's mise.toml as
its [env] table, which mise applies to the daemon and to everything the daemon
spawns:

  helm upgrade {{ .Release.Name }} <chart> --reuse-values \
    --set toolEnv.CARGO_HOME=/cache/cargo \
    --set toolEnv.GOCACHE=/cache/go-build

Every tool has its own cache variable and mise cannot infer them, so this map is
empty by default for the same reason `tools` is: the variables follow from the
tools you pinned. Pointing them at /cache (the {{ ((.Values.storage).cache).size | default "5Gi" }} claim) keeps disposable
registries off the durable /zeroclaw-data volume — the per-tool list is in the
chart README, and in mise.toml.example section 3.

Do not set the image's own mise variables here (MISE_DATA_DIR, MISE_RUSTUP_HOME,
MISE_CACHE_DIR): mise reads them before mise.toml exists, so restating them
desynchronises the paths it has already installed into.

The ZeroClaw gateway is fronted by a {{ ((.Values.gateway).service).type | default "ClusterIP" }} Service — cluster-internal
only, no Ingress and no TLS. With the documented release name the Service is
`{{ .Release.Name }}`:

  kubectl -n {{ .Release.Namespace }} get svc {{ .Release.Name }}
  kubectl -n {{ .Release.Namespace }} port-forward svc/{{ .Release.Name }} {{ ((.Values.gateway).service).port | default 42617 }}:{{ ((.Values.gateway).service).port | default 42617 }}

{{- else }}

No Service is rendered and the daemon listens on loopback only:

  kubectl -n {{ .Release.Namespace }} port-forward {{ .Release.Name }}-0 42617:42617

{{- end }}

/health IS UNAUTHENTICATED. It reports pairing state (`paired`,
`require_pairing`) and a runtime health snapshot. That is acceptable from inside
the cluster, which is why the Service is ClusterIP and not LoadBalancer or
Ingress — if you add one, terminate authentication in front of it.

No probes, by design. The pod reports Ready the moment the container is Running,
so "install succeeded" and "the agent works" are two different facts, and a
wedged agent is not restarted automatically. Watch the logs:

  kubectl -n {{ .Release.Namespace }} logs -f <pod> -c main

The volumes are retained, so `helm uninstall` does not delete them. A plain
reinstall afterwards fails on the existing claims — adopt them
(storage.<volume>.existingClaim) or delete them and accept the re-download.
